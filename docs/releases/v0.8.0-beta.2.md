# Zodvex 0.8.0-beta.2

## Optional customization patches retain fallback types

Fixed a handler-inference regression introduced by PR #141 and present in
`0.8.0-beta.1`. A customization returning `args: { count?: string }` could make
TypeScript accept `args.count?.toUpperCase()` even when the function declared
`count: z.number()`. If the customization omitted `count`, runtime object spread
retained the number and the handler threw a `TypeError`.

Public handler arguments and contexts now use the same `MergePatch`/`SpreadPatch`
types as runtime customization composition. For a required numeric argument and
an optional string replacement, the handler sees `number | string | undefined`:

- An omitted replacement retains the original number.
- A present string replaces the number.
- An explicitly present `undefined` overwrites the number with `undefined`.

The argument key remains required. A required string replacement still produces
`string`, with no numeric fallback. Handlers with optional replacements must
narrow the value before calling string methods, for example:

```ts
handler: (_ctx, args) =>
  typeof args.count === 'string' ? args.count.toUpperCase() : String(args.count)
```

The correction also covers context patches, codec/user context composition,
`defineContext`, legacy custom builders, and full-Zod/Mini server entrypoints.
Runtime spread behavior and ID validation are unchanged. Customizations returning
`args: {}`, including Hotpot's current customizations, retain their existing types
and behavior; this report does not establish a current Hotpot runtime failure.

### Verification

The minimal `initZodvex(..., { wrapDb: false })` query reproduction was checked in
an isolated consumer with TypeScript 5.9.3 (`strict: true`), Zod 4.6.5, Convex
1.42.0, and convex-helpers 0.1.104. Published `0.8.0-beta.1` accepted it and its
local `_handler({}, { count: 42 })` threw `TypeError`. Published `0.7.11` rejected
the same handler with TS2339. Current main at `01667e4` had the same public typing
gap as the beta.

Regression coverage checks required, omitted optional, present optional, and
explicitly undefined patches across all six `initZodvex` builders, Zod and Mini
schemas, context composition, and emitted consumer declarations. Local validation
`bun run validate:local` passed, including 2,480 library runtime tests, type
checks, builds, consumer declarations, codemod tests, local example checks, and
generated-file freshness. The rebuilt declarations reject the original unsafe
handler with TS2339 on `string | number`. No deployment, release, or cloud
benchmark was run.

### Release automation

Merging this version bump into `main` starts the existing release validation and
publishing pipeline for `0.8.0-beta.2`, using npm's `beta` dist-tag. Subsequent main
pushes skip versions that already have a Git tag. Only untagged numeric `alpha`,
`beta`, and `rc` prereleases are released automatically; stable versions still
require an explicit tag, release branch, or workflow dispatch. Failed publishing
can be retried through the existing manual release workflow on the tagged commit.

The local `bin/release-beta` path pushes main and its tag atomically, so only the
tag workflow publishes; a rejected tag also prevents main from advancing.
`bun run verify:release`, included in local validation and CI, exercises the
workflow's actual planning shell and the release script against a local bare Git
remote, including tag rejection. These checks do not publish anything.
